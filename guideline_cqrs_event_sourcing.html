CQRS com Event Sourcing

Guia de implementação a nível de negócio para o domínio CRM de corretora de valores.
Agnóstico a tecnologia — sem referências a frameworks ou linguagens.

1. Visão Geral da Arquitetura

Este guideline descreve como implementar duas aplicações independentes que juntas formam o sistema de CQRS com Event Sourcing: uma aplicação de escrita e uma de leitura. Elas se comunicam por uma fila de mensagens assíncrona.

Princípio central: a aplicação de escrita nunca lê do banco de leitura, e a aplicação de leitura nunca escreve eventos. A fronteira entre elas é a fila de mensagens.
ℹ
Por que duas aplicações separadas? O volume de consultas é 10.000× maior que o volume de transações. Separar escrita de leitura em processos distintos permite escalar cada lado de forma independente. A Read App pode ter múltiplas réplicas servindo queries enquanto a Write App permanece focada em garantir a consistência do domínio.

2. Domínio de Negócio

O domínio implementado é um CRM de corretora de valores. As principais regras de negócio que guiam as decisões de implementação são:

⚖ Regras que impactam a arquitetura
  • Volume assimétrico: o volume de leitura (listagem de clientes pelos gerentes) é 10.000× maior que o volume de escrita (transações financeiras). Este é o principal motivador para CQRS.
  • Baixa frequência de escrita: clientes realizam grandes aportes com baixíssima frequência (perfil de longo prazo). O Event Store crescerá lentamente para a maioria dos clientes.
  • Múltiplas carteiras por cliente: um cliente pode ser titular de mais de uma carteira (e.g. patrimônio familiar ou societário). A projeção de leitura deve consolidar todas elas.
  • Wallet é um microsserviço separado: tanto o CRM quanto o aplicativo da corretora consomem o mesmo microsserviço de Wallet. O CRM não é dono das transações — ele as observa como eventos de domínio emitidos pelo Wallet.
  • Transações confirmadas pela Bolsa: uma transação só é salva quando confirmada pela Bolsa de Valores. O comando de registro de transação deve aguardar essa confirmação antes de ser considerado aceito.
  • Janela de operações: transações só são processadas de segunda a sexta, das 8h às 19h. O sistema de escrita deve validar essa invariante.
  • Gerentes com perfil admin: alguns gerentes enxergam todos os clientes da corretora em uma única listagem. O modelo de leitura deve suportar essa visão sem comprometer a performance.
  • Listagem com filtros e ordenações: gerentes usam filtros e ordenações como ferramenta de relacionamento para decidir quem contatar. O modelo de leitura deve ser projetado especificamente para esse caso de uso.

Bounded Contexts

O domínio se divide em três contextos delimitados. Este guideline implementa apenas o CRM Context e define como ele consome eventos do Wallet Context.

Revenue Context Controlar receita por filial e mês. Fora do escopo

3. Princípios do Event Sourcing

Antes de especificar a implementação, o agente deve internalizar os conceitos centrais do Event Sourcing, pois eles impactam cada decisão de design.

Estado = Replay de Eventos

O estado atual de um aggregate não é armazenado diretamente. Ele é sempre recalculado aplicando todos os eventos passados em sequência. O banco de dados da Write App é o Event Store — uma lista imutável e append-only de eventos.

Eventos são Fatos Imutáveis

Um evento representa algo que já aconteceu no domínio. Nunca é deletado ou modificado. Se um erro ocorre, um novo evento de correção é emitido. Isso cria um log de auditoria completo e natural.

Consistência Eventual entre Write e Read

A Write App garante consistência forte dentro do aggregate. A Read App será atualizada de forma assíncrona — há uma janela de tempo entre a escrita e a atualização da projeção. Este é o trade-off central do CQRS com ES.

Snapshots como Otimização

Com o tempo, reconstruir o estado de uma Wallet replaying 500 transações fica lento. Snapshots capturam o estado do aggregate em um ponto no tempo, evitando o replay desde o início. São uma otimização — nunca uma necessidade correta, mas praticamente obrigatória em produção.

4. Aggregates da Write App

Um aggregate é a unidade de consistência do domínio. Toda operação de escrita deve passar por um aggregate. O aggregate valida invariantes de negócio e emite eventos — nunca persiste estado diretamente.

5. Commands

Um command representa a intenção de mudar o estado do sistema. É uma mensagem que vai para o aggregate correto. Nunca retorna dados de domínio — apenas sucesso/falha.

📐 Estrutura de um Command
  • aggregateId: identifica o aggregate-alvo (obrigatório em updates/actions, ausente em creates)
  • payload: dados necessários para executar a intenção
  • metadata: quem está enviando, timestamp, correlationId para rastreabilidade
  • Sem lógica de negócio — é apenas um envelope de dados

Commands do Wallet Context

CommandDados necessáriosPrecondições
CreateWallet customerId Customer deve existir
RegisterTransaction walletId, value, type (DEPOSIT/WITHDRAWAL), exchangeConfirmationId Wallet deve existir · Janela de horário válida · Confirmação da Bolsa presente · Valor positivo

Commands do CRM Context

CommandDados necessáriosPrecondições

CreateAccountManager name, branchId, isAdmin Branch deve existir
GrantAdminProfile accountManagerId AccountManager deve existir · Não pode já ser admin

6. Eventos de Domínio

Eventos são a fonte da verdade do sistema. Ao contrário de comandos, eventos são sempre nomeados no passado (algo que ocorreu). Uma vez persistido no Event Store, um evento nunca muda.

Anatomia de um evento

Todo evento deve carregar os seguintes campos:

{
  "eventId": "uuid-v4",          // identificador único do evento
  "eventType": "TransactionRegistered", // nome do evento (PascalCase)
  "aggregateId": "uuid-da-wallet",  // aggregate ao qual pertence
  "aggregateType": "Wallet",       // tipo do aggregate
  "version": 42,               // posição sequencial no stream
  "occurredAt": "2025-11-01T14:32:00Z", // quando aconteceu
  "payload": {                // dados específicos do evento
    "value": 50000.00,
    "type": "DEPOSIT",
    "exchangeConfirmationId": "uuid-confirmacao"
  },
  "metadata": {
    "correlationId": "uuid-do-command", // rastreia o command que gerou
    "causedBy": "customerId:uuid"    // quem causou
  }
}
⚠
O campo version é crítico. Ele garante ordenação e permite detecção de conflitos de concorrência. Ao persistir um evento, o Event Store deve verificar que a versão esperada corresponde à versão atual do stream. Se divergir, o comando deve ser rejeitado (optimistic locking).

7. Event Store

O Event Store é o banco de dados da Write App. Ele não é um banco de dados relacional comum — é um log append-only de eventos ordenados por aggregate. Pense nele como um diário imutável.

Estrutura conceitual do Event Store

📦 Tabela de eventos (conceitual)
  • stream_id: identificador do aggregate (e.g. Wallet-uuid-123)
  • version: número sequencial dentro do stream, começa em 0
  • event_type: nome do evento
  • payload: dados serializados do evento
  • metadata: correlationId, causedBy, etc.
  • occurred_at: timestamp de quando o evento ocorreu no domínio
  • stored_at: timestamp de quando foi persistido (pode diferir)
  • Chave única: (stream_id, version) — garante o optimistic locking

Operações do Event Store

AppendEvents(streamId, expectedVersion, events[])

Persiste novos eventos no stream. Verifica que a versão atual do stream corresponde ao expectedVersion. Se houver discrepância (outro processo escreveu antes), lança conflito de concorrência. Esta é a única operação de escrita do Event Store.

LoadStream(streamId, fromVersion?)

Carrega todos os eventos de um aggregate em ordem crescente de version. O parâmetro opcional fromVersion permite carregar apenas eventos após um snapshot.

GetCurrentVersion(streamId)

Retorna a versão mais recente de um stream. Usado para montar o expectedVersion antes de processar um command.

8. Command Handlers

O Command Handler é o orquestrador do fluxo de escrita. Ele conecta o command ao aggregate e ao Event Store. Nunca contém lógica de negócio — a lógica fica no aggregate. O handler apenas coordena.

Fluxo padrão de um Command Handler

1
Command Handler
Recebe o command e valida a estrutura (campos obrigatórios presentes, tipos corretos)
Esta é uma validação técnica, não de negócio. Ex.: "o campo walletId é um UUID válido?"
2
Command Handler → Event Store
Carrega o stream de eventos do aggregate via LoadStream(aggregateId)
Se for um command de criação (Create*), o stream estará vazio — comportamento esperado
3
Command Handler → Aggregate
Reconstrói o estado atual do aggregate aplicando os eventos carregados em sequência
O aggregate vai aplicando cada evento no seu estado interno: apply(event)
4
Aggregate
Executa o command: valida invariantes de negócio e emite novos eventos
Se uma invariante for violada, lança exceção de domínio. Se válido, retorna lista de novos eventos
5
Command Handler → Event Store
Persiste os novos eventos via AppendEvents(aggregateId, currentVersion, newEvents)
Em caso de conflito de versão, o handler pode fazer retry ou propagar o erro
6
Command Handler → Fila
Publica os novos eventos na fila de mensagens para consumo pela Read App
Esta publicação deve ser feita após a persistência no Event Store ser confirmada
🔴
Publicar na fila antes de persistir no Event Store é um bug crítico. Se o sistema falhar entre a publicação e a persistência, a Read App processará um evento que nunca foi confirmado na Write App, criando inconsistência permanente. A ordem correta é: persistir → publicar.

9. Fila de Mensagens

A fila é o canal de comunicação entre a Write App e a Read App. Ela desacopla temporalmente as duas aplicações e garante que eventos sejam entregues mesmo que a Read App esteja temporariamente indisponível.

📋 Requisitos funcionais da fila
  • Garantia de entrega: a fila deve garantir at-least-once delivery. A Read App deve ser idempotente para lidar com reentregas.
  • Ordenação por aggregate: eventos do mesmo aggregate devem ser processados em ordem. Eventos de aggregates diferentes podem ser processados em paralelo.
  • Dead Letter Queue (DLQ): eventos que falham repetidamente devem ser enviados para uma fila de mensagens mortas para inspeção manual — nunca descartados silenciosamente.
  • Visibilidade de mensagens: uma mensagem em processamento deve ficar invisível para outros consumidores até ser confirmada (acked) ou expirar.
  • Mensagem mínima: a mensagem publicada na fila deve conter o evento completo (mesma estrutura do Event Store), incluindo version e aggregateId.
ℹ
Sobre idempotência na Read App: como a fila garante at-least-once (e não exactly-once), a Read App pode receber o mesmo evento duas vezes. O consumer deve verificar se o evento já foi processado antes de atualizar a projeção. A forma mais simples é guardar o eventId como chave de idempotência na Read App.

Contratos de mensagem publicados

A Write App publica na fila um evento por mensagem. Cada mensagem deve incluir:

  • O payload completo do evento (mesma estrutura do Event Store)
  • O campo aggregateId como chave de agrupamento para garantir ordenação
  • O campo version para que a Read App possa detectar eventos fora de ordem

10. Consumer da Read App

O Consumer é o componente da Read App responsável por escutar a fila e acionar as projeções. Ele deve ser stateless — todo estado fica na projeção.

Fluxo do Consumer

1
Consumer
Recebe a mensagem da fila e deserializa o evento
2
Consumer → Banco da Read App
Verifica se o eventId já foi processado (controle de idempotência)
Se já processado, confirma a mensagem na fila (ack) e ignora. Não é um erro.
3
Consumer → Projeção correta
Roteia o evento para o handler de projeção correspondente ao eventType
Ex.: TransactionRegistered → CustomerViewProjection.handleTransactionRegistered(event)
4
Projeção → Banco da Read App
Atualiza o modelo de leitura com base nos dados do evento
5
Consumer → Fila
Confirma o processamento da mensagem (ack)
Só confirma após a projeção ser atualizada com sucesso no banco

11. Projeções (Read Models)

Uma projeção é uma visão desnormalizada dos dados, otimizada para uma query específica. Ela é reconstruída a partir dos eventos. O banco da Read App é separado do Event Store e pode ter uma estrutura completamente diferente.

11.1 CustomerView — projeção principal

Esta é a projeção central do sistema. Ela combina dados de múltiplos aggregates em uma única estrutura pronta para exibição. O gerente de conta visualiza esta projeção na tela de listagem.

📊 Estrutura do CustomerView (modelo de leitura)
  • customerId — identificador do cliente
  • customerName — nome completo do cliente
  • customerAge — idade
  • customerAddress — endereço
  • accountManagerId — id do gerente responsável
  • managerName — nome do gerente (desnormalizado)
  • branchId — id da filial
  • branchRegion — região da filial (desnormalizado)
  • wallets[] — lista de carteiras do cliente:
    • walletId
    • balance — saldo calculado (soma de DEPOSIT - WITHDRAWAL)
    • transactions[] — histórico de transações:
      • transactionId, value, type, occurredAt
  • totalBalance — saldo consolidado de todas as carteiras (calculado)
  • lastTransactionAt — data da última movimentação (para filtros do gerente)
  • updatedAt — quando a projeção foi atualizada pela última vez

Mapeamento eventos → CustomerView

Cada evento produz uma atualização específica na projeção:

Evento recebidoO que atualizar no CustomerView
CustomerCreated Criar novo registro de CustomerView com os dados do cliente. accountManagerId será resolvido para nome na próxima etapa ou quando AccountManagerCreated já estiver processado.
CustomerDataUpdated Atualizar customerName, customerAddress ou customerAge conforme campos presentes no payload.
AccountManagerAssigned Atualizar accountManagerId, managerName e branchRegion no CustomerView do cliente afetado.
AccountManagerCreated Criar registro de AccountManager no banco de leitura. Não impacta CustomerView diretamente ainda.
BranchAssigned Atualizar branchRegion em todos os CustomerViews cujo gerente seja o AccountManager afetado.
WalletCreated Adicionar nova wallet na lista wallets[] do CustomerView correspondente ao customerId.
TransactionRegistered Adicionar transação em transactions[] da wallet correta · Recalcular balance da wallet · Recalcular totalBalance do CustomerView · Atualizar lastTransactionAt.
⚠
Dependência entre eventos: ao processar CustomerCreated, é possível que AccountManagerCreated ainda não tenha sido processado (eventos chegam de aggregates diferentes). A projeção deve lidar com essa situação — uma estratégia é armazenar o accountManagerId e resolver o nome em uma etapa posterior, ou tolerar temporariamente campos nulos na projeção.

11.2 AccountManagerDashboard — visão admin

Projeção secundária para gerentes com perfil administrativo. Exibe todos os clientes da corretora com os mesmos dados do CustomerView, sem filtro por gerente.

📊 Estrutura do AccountManagerDashboard
  • Lista paginada de CustomerViews de todos os clientes
  • Metadados de paginação: total de registros, página atual
  • Suporte a filtros: por gerente, por filial, por saldo mínimo, por data de última transação
  • Suporte a ordenação: por nome, por saldo, por data da última transação
  • É alimentado pelos mesmos eventos que o CustomerView — não requer novos eventos

12. Estratégia de Snapshot

Snapshots evitam o replay de toda a história de eventos de um aggregate ao reconstruir seu estado. Para o aggregate Wallet, isso é obrigatório — um cliente ativo há 10 anos pode ter centenas de transações.

📐 Dados de um Snapshot
  • aggregateId: qual aggregate este snapshot representa
  • aggregateType: tipo do aggregate
  • version: versão do stream no momento do snapshot
  • state: estado serializado completo do aggregate naquela versão
  • createdAt: quando o snapshot foi criado

Política de criação de snapshot

Quando criar

Criar um snapshot sempre que o número de eventos desde o último snapshot atingir um limiar definido. Para o aggregate Wallet, recomenda-se a cada 50 eventos dado o perfil de baixa frequência de transações. O limiar exato pode ser ajustado durante os testes de carga.

Como carregar com snapshot

Ao receber um command para uma Wallet: (1) buscar o snapshot mais recente → (2) carregar eventos com version > snapshotVersion → (3) aplicar snapshot no aggregate → (4) aplicar eventos restantes. Se não houver snapshot, carregar todos os eventos desde o início.

Onde armazenar

Snapshots são armazenados em uma tabela separada do Event Store, mas no mesmo banco de dados da Write App. Nunca substituem eventos — os eventos originais são mantidos para auditoria completa.

13. Queries da Read App

Queries são consultas ao banco de leitura. Ao contrário dos commands, retornam dados diretamente e nunca alteram estado. O banco de leitura deve ser otimizado especificamente para estas queries.

QueryParâmetrosRetornoCaso de uso
GetCustomerView customerId CustomerView completo Gerente visualiza ficha de um cliente
ListCustomersByManager accountManagerId, filtros?, ordenação?, página? Lista paginada de CustomerViews Gerente vê seus clientes com filtros
ListAllCustomers filtros?, ordenação?, página? Lista paginada de todos os CustomerViews Gerente admin vê todos os clientes

Filtros suportados na listagem

Os gerentes usam filtros ativamente como ferramenta de trabalho de relacionamento. O banco de leitura deve suportar eficientemente:

  • Filtro por accountManagerId — gerente filtra seus próprios clientes
  • Filtro por branchId — admin filtra por filial
  • Filtro por totalBalance mínimo/máximo — para identificar perfis de alto patrimônio
  • Filtro por lastTransactionAt — para identificar clientes sem movimentação recente
  • Ordenação por customerName, totalBalance, lastTransactionAt

17. Critérios de Aceite

O agente implementador deve garantir que todos os itens abaixo estão funcionando antes de considerar a implementação completa.

Write App

  • Aggregate Wallet: ao aplicar N eventos em sequência, o estado reconstruído é idêntico ao esperado (balance = soma de DEPOSIT - WITHDRAWAL)
  • Invariante de horário: command RegisterTransaction fora da janela 08h–19h ou em fim de semana deve ser rejeitado com erro de domínio
  • Invariante de valor: command com value ≤ 0 deve ser rejeitado
  • Optimistic locking: dois commands simultâneos para a mesma Wallet devem resultar em um sucesso e um conflito de versão
  • Event Store: após qualquer command aceito, o evento correspondente está persistido com version incrementada
  • Publicação na fila: evento é publicado na fila somente após persistência confirmada no Event Store
  • Snapshot criado: após N transações em uma Wallet, um snapshot é criado no banco
  • Reconstituição com snapshot: carregar Wallet via snapshot + delta produz o mesmo estado que carregar todos os eventos desde o início

Fila e Consumer

  • Reentrega idempotente: processar o mesmo evento duas vezes não produz dados duplicados na projeção
  • DLQ configurada: evento que falha repetidamente vai para Dead Letter Queue, não é descartado
  • Ordenação por aggregate: eventos da mesma Wallet são processados na ordem correta de version

Read App

  • CustomerView completo: após CustomerCreated + WalletCreated + TransactionRegistered, o CustomerView contém nome, gerente, filial, saldo e transação
  • Múltiplas carteiras: cliente com 2 wallets tem ambas listadas e totalBalance é a soma de ambas
  • Filtro por saldo: query com saldo mínimo retorna apenas clientes com totalBalance ≥ filtro
  • Filtro por última transação: query com data retorna apenas clientes com lastTransactionAt dentro do período
  • Perfil admin: gerente sem perfil admin não acessa ListAllCustomers
  • Consistência eventual: após uma transação ser confirmada na Write App, a Read App deve refletir o novo saldo em um tempo aceitável (definido durante os testes de carga)

Qualidade de código (para análise SonarQube)

  • Cada aggregate deve ter testes unitários cobrindo todas as invariantes de negócio
  • Cada projeção deve ter testes de integração cobrindo o mapeamento evento → leitura
  • Command Handlers devem ter testes cobrindo o fluxo completo com mocks do Event Store e da fila
  • Complexidade ciclomática individual de métodos deve ser mantida baixa — extrair métodos quando um handler acumula muita lógica
ℹ
Nota para o TCC: este guideline foi desenhado para maximizar a complexidade mensurável — aggregates com invariantes, snapshots como controle de estado, consumer com idempotência, projeções com cálculos — sem adicionar complexidade artificial. O SonarQube deve capturar McCabe e Halstead naturalmente dessa implementação.
