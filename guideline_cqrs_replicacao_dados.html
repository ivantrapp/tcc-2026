CQRS com Replicação de Dados

Guia de implementação baseado na abordagem de Renani (2024) para o domínio CRM de corretora de valores. Usa replicação lógica nativa do PostgreSQL como mecanismo de sincronização entre Write e Read.

1. Visão Geral da Arquitetura

Esta abordagem implementa CQRS substituindo o Event Sourcing e a fila de mensagens por um mecanismo já nativo do PostgreSQL: a replicação lógica via WAL. O resultado é uma arquitetura com menos componentes e menos código de infraestrutura, onde a sincronização entre os dois bancos é responsabilidade do próprio banco de dados.

O que desaparece em relação ao Event Sourcing: não há Event Store, não há fila de mensagens, não há consumer, não há projeções em código, não há snapshots. A sincronização é inteiramente gerenciada pelo PostgreSQL.

2. Diferenças Fundamentais em Relação ao Event Sourcing

O agente deve entender onde as duas abordagens divergem para não aplicar padrões do ES nesta implementação. As diferenças são profundas e afetam cada camada do sistema.

Event Sourcing
  • Estado reconstruído por replay de eventos
  • Banco write é um Event Store append-only
  • Sincronização via fila de mensagens
  • Read side mantém projeções em código
  • Snapshot necessário para performance
  • Histórico completo de mudanças disponível
  • Consumer com controle de idempotência
Replicação de Dados
  • Estado armazenado diretamente em tabelas
  • Banco write é um banco relacional comum
  • Sincronização via replicação WAL do PostgreSQL
  • Read side usa views SQL sobre tabelas replicadas
  • Sem snapshot — estado sempre atual
  • Apenas estado atual disponível (sem histórico de mudanças)
  • Sem consumer — PostgreSQL entrega automaticamente

O que permanece igual

As duas abordagens compartilham a mesma estrutura de aggregates, commands e handlers na Write App. A lógica de negócio — invariantes, validações, domínio — é idêntica. O que muda é o que acontece após o aggregate validar e persistir.

⚠
Trade-off central desta abordagem: ao armazenar somente o estado atual, o sistema perde o histórico de mudanças. Se um gerente precisar saber "qual era o saldo desta carteira em março de 2023", esta arquitetura não responde. O Event Sourcing responderia, pois os eventos são imutáveis. Este é o trade-off que o TCC deve documentar.

3. Como Funciona a Replicação Lógica do PostgreSQL (WAL)

Para implementar corretamente, o agente precisa entender o mecanismo que substitui a fila de mensagens nesta arquitetura.

O que é o WAL (Write-Ahead Log)

O PostgreSQL mantém um registro sequencial de toda operação de escrita antes de aplicá-la nas tabelas. Esse registro chama-se WAL. Ele existe primariamente para garantir durabilidade e recuperação após falhas — mas o PostgreSQL expõe este log para que outros sistemas possam consumi-lo. É isso que torna a replicação possível sem nenhuma ferramenta externa.

Replicação Lógica vs. Física

A replicação física copia blocos de disco inteiros — é um espelho byte-a-byte, usado para alta disponibilidade. A replicação lógica copia as operações no nível de linha (INSERT, UPDATE, DELETE em tabelas específicas), o que permite replicar apenas um subconjunto de tabelas e manter esquemas diferentes nos dois bancos. É a replicação lógica que esta arquitetura usa.

Tudo dentro do PostgreSQL. Latência de microssegundos em mesma rede (Renani, 2024).
Publicação e Subscrição

O modelo de replicação lógica usa um padrão publisher/subscriber nativo. O banco de escrita configura uma publicação declarando quais tabelas serão replicadas. O banco de leitura configura uma subscrição apontando para essa publicação. A partir daí, toda mudança nas tabelas publicadas é propagada automaticamente para o banco de leitura — sem código, sem fila, sem consumer.

Consistência Eventual

A replicação é assíncrona por padrão. Após um INSERT no banco de escrita, há uma janela de tempo até que o banco de leitura receba a mudança. Em ambiente de mesma rede, Renani (2024) mediu esta latência na casa dos microssegundos em condições idle. Sob carga, esta janela pode crescer — o que os testes de carga do TCC irão quantificar.

4. Aggregates da Write App

Os aggregates desta implementação têm as mesmas responsabilidades de negócio que no Event Sourcing: validar invariantes e autorizar mudanças de estado. A diferença é que, em vez de emitir eventos que são persistidos no Event Store, o aggregate retorna o estado atualizado que será salvo diretamente em tabelas relacionais.

ℹ
Mudança conceitual importante: no Event Sourcing, o aggregate emite eventos e o estado é uma consequência do replay. Aqui, o aggregate valida e retorna o novo estado. O handler persiste esse estado diretamente. Não há eventos, não há replay.

6. Command Handlers

O fluxo do handler é mais direto que no Event Sourcing: carregar o aggregate do banco, validar, persistir o novo estado. Sem Event Store, sem publicação em fila.

Fluxo padrão de um Command Handler

1
Command Handler
Recebe o command e valida a estrutura técnica (campos obrigatórios, tipos)
2
Command Handler → Banco Write
Carrega o estado atual do aggregate direto da tabela relacional
Para um command de criação (Create*), o aggregate começa vazio. Para updates, carrega a linha existente.
3
Aggregate
Recebe o command, valida as invariantes de negócio e retorna o novo estado
Se uma invariante for violada, lança exceção de domínio. Se válido, retorna o aggregate com estado atualizado.
4
Command Handler → Banco Write
Persiste o novo estado via INSERT ou UPDATE na tabela correspondente
O PostgreSQL registra a operação no WAL automaticamente. A replicação para o banco read começa imediatamente após o commit.
5
PostgreSQL (automático)
O mecanismo de replicação lógica propaga a mudança para o banco de leitura sem nenhuma ação do código da aplicação
O handler não precisa saber que existe um banco de leitura. Esta é uma responsabilidade da infraestrutura de banco.
✓
Vantagem direta: o handler é significativamente mais simples que no Event Sourcing. Não há lógica de versão, não há publicação em fila, não há tratamento de conflito de versão. Isso se reflete diretamente nas métricas de complexidade ciclomática que o SonarQube irá medir.

7. Banco de Dados Write — Estrutura das Tabelas

O banco write é um PostgreSQL relacional comum. As tabelas armazenam o estado atual dos aggregates, não eventos. A estrutura segue o diagrama de classes do domínio.

● Write DB — tabelas do domínio
-- Domínio CRM
CREATE TABLE branches (
  id        UUID PRIMARY KEY,
  region    TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE account_managers (
  id        UUID PRIMARY KEY,
  name      TEXT NOT NULL,
  branch_id  UUID REFERENCES branches(id),
  is_admin   BOOLEAN NOT NULL DEFAULT FALSE,
  created_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE customers (
  id                UUID PRIMARY KEY,
  name              TEXT NOT NULL,
  address           TEXT,
  age               INT NOT NULL,
  account_manager_id UUID REFERENCES account_managers(id),
  created_at        TIMESTAMPTZ NOT NULL
);

-- Domínio Wallet (microsserviço separado, mesmo servidor para fins deste projeto)
CREATE TABLE wallets (
  id          UUID PRIMARY KEY,
  customer_id UUID REFERENCES customers(id),
  balance     NUMERIC(18,2) NOT NULL DEFAULT 0,
  created_at  TIMESTAMPTZ NOT NULL
);

CREATE TABLE transactions (
  id                      UUID PRIMARY KEY,
  wallet_id              UUID REFERENCES wallets(id),
  value                  NUMERIC(18,2) NOT NULL,
  type                   TEXT NOT NULL, -- 'DEPOSIT' ou 'WITHDRAWAL'
  exchange_confirmation_id UUID NOT NULL,
  occurred_at            TIMESTAMPTZ NOT NULL
);
ℹ
Sobre o campo balance na tabela wallets: o saldo é mantido como coluna diretamente na tabela, atualizado a cada transação registrada. Isso difere do Event Sourcing onde o saldo era calculado somando as transações. Aqui, o handler faz o cálculo e persiste o resultado — simplificando as queries de leitura.

8. Configuração da Publicação no Banco Write

A publicação declara ao PostgreSQL quais tabelas do banco write serão monitoradas para replicação. É uma configuração feita uma vez no banco de dados, não no código da aplicação.

● Write DB — configuração da publicação
-- Pré-requisito: o banco write deve ter wal_level = 'logical' no postgresql.conf
-- Isso habilita a decodificação lógica do WAL

-- Criar a publicação declarando quais tabelas participam da replicação
CREATE PUBLICATION crm_publication FOR TABLE
  customers,
  account_managers,
  branches,
  wallets,
  transactions;

-- A publicação captura INSERT, UPDATE e DELETE por padrão
-- Para apenas INSERT e UPDATE (sem deletar no read): usar WITH (publish = 'insert, update')
📋 O que a publicação captura por tabela
  • customers: INSERT ao criar cliente, UPDATE ao alterar dados ou reatribuir gerente
  • account_managers: INSERT ao criar gerente, UPDATE ao conceder admin ou reatribuir filial
  • branches: INSERT ao criar filial — operação rara, mas precisa ser replicada
  • wallets: INSERT ao criar carteira, UPDATE ao alterar o saldo após transação
  • transactions: INSERT ao registrar transação — nunca há UPDATE ou DELETE em transações
⚠
Pré-requisito de chave primária: para que a replicação lógica funcione com UPDATE e DELETE, todas as tabelas publicadas devem ter chave primária definida. O PostgreSQL precisa dela para identificar qual linha replicar no banco de leitura. Todas as tabelas desta arquitetura usam UUID PRIMARY KEY, o que satisfaz este requisito.

9. Configuração da Subscrição no Banco Read

O banco de leitura configura uma subscrição que aponta para a publicação do banco de escrita. A partir da criação da subscrição, o PostgreSQL passa a entregar automaticamente todas as mudanças publicadas.

● Read DB — estrutura e subscrição
-- As tabelas no banco de leitura devem ter a mesma estrutura das publicadas
-- (mesmos nomes de colunas e tipos). O PostgreSQL exige isso para a replicação funcionar.

CREATE TABLE customers ( /* mesma estrutura do write DB */ );
CREATE TABLE account_managers ( /* mesma estrutura */ );
CREATE TABLE branches ( /* mesma estrutura */ );
CREATE TABLE wallets ( /* mesma estrutura */ );
CREATE TABLE transactions ( /* mesma estrutura */ );

-- Criar a subscrição apontando para o banco de escrita
CREATE SUBSCRIPTION crm_subscription
  CONNECTION 'host=write-db-host dbname=crm_write user=replicator password=...'
  PUBLICATION crm_publication;

-- A partir deste momento, o PostgreSQL sincroniza automaticamente.
-- O sync inicial copia todos os dados existentes antes de iniciar o streaming.
ℹ
Sincronização inicial: ao criar a subscrição, o PostgreSQL realiza automaticamente uma cópia completa dos dados existentes nas tabelas publicadas antes de iniciar o streaming de novos eventos. Isso significa que o banco de leitura começa vazio e é populado pelo próprio mecanismo de replicação.

10. Cuidados Operacionais com a Replicação

A replicação lógica tem comportamentos específicos que o agente deve conhecer para evitar problemas durante a implementação.

Mudanças de esquema (migrations)

A replicação lógica não replica DDL (CREATE TABLE, ALTER TABLE, etc.) — apenas DML (INSERT, UPDATE, DELETE). Se uma coluna for adicionada ao banco write, ela deve ser adicionada manualmente ao banco read também, antes que dados com essa coluna comecem a chegar via replicação. Migrations exigem coordenação entre os dois bancos. Para este projeto de TCC, onde o esquema é fixo, isso não é um problema prático.

Foreign keys no banco de leitura

O banco de leitura não deve ter foreign keys nas tabelas replicadas. Como a replicação pode entregar dados em ordem imprevisível (e.g. uma transação chegando antes da wallet correspondente), as foreign keys causariam erros de violação de integridade referencial. As restrições de integridade já são garantidas pelo banco write — no banco read, as tabelas são apenas réplicas para leitura.

Replication slot e WAL retention

O PostgreSQL mantém os segmentos do WAL acumulados enquanto o banco de leitura não confirmar que os processou. Se o banco de leitura ficar indisponível por muito tempo, o WAL pode crescer indefinidamente e encher o disco do banco write. Para este projeto, ambos os bancos estarão rodando na mesma infraestrutura, minimizando este risco.

Usuário de replicação

O banco write precisa de um usuário PostgreSQL com o atributo REPLICATION concedido e permissão de leitura nas tabelas publicadas. Este usuário é usado exclusivamente pela subscrição do banco read — a aplicação nunca o usa diretamente.

12. Views SQL — O Modelo de Leitura

As views substituem as projeções em código do Event Sourcing. Em vez de um consumer processando eventos e montando o modelo de leitura em memória, aqui o próprio SQL compõe a visão desnormalizada a partir das tabelas replicadas. Nenhum código de aplicação é necessário para montar o CustomerView.

12.1 View customer_view

É a view central do sistema. Compõe em uma única consulta os dados de cliente, gerente, filial e todas as carteiras com seus saldos e transações. O gerente de conta consulta esta view diretamente.

● Read DB — view customer_view
CREATE VIEW customer_view AS
SELECT
  c.id                     AS customer_id,
  c.name                   AS customer_name,
  c.age                    AS customer_age,
  c.address                AS customer_address,
  am.id                    AS account_manager_id,
  am.name                  AS manager_name,
  am.is_admin              AS manager_is_admin,
  b.id                     AS branch_id,
  b.region                 AS branch_region,
  COALESCE(SUM(w.balance), 0)  AS total_balance,
  MAX(t.occurred_at)      AS last_transaction_at
FROM customers c
LEFT JOIN account_managers am ON am.id = c.account_manager_id
LEFT JOIN branches b ON b.id = am.branch_id
LEFT JOIN wallets w ON w.customer_id = c.id
LEFT JOIN transactions t ON t.wallet_id = w.id
GROUP BY c.id, c.name, c.age, c.address,
         am.id, am.name, am.is_admin,
         b.id, b.region;

-- Esta view entrega em uma única query: nome, gerente, filial,
-- saldo consolidado de todas as carteiras e data da última transação.

12.2 View de transações por cliente

View separada para o histórico detalhado de transações, usada quando o gerente abre o perfil de um cliente específico.

● Read DB — view customer_transactions_view
CREATE VIEW customer_transactions_view AS
SELECT
  c.id          AS customer_id,
  w.id          AS wallet_id,
  w.balance     AS wallet_balance,
  t.id          AS transaction_id,
  t.value       AS transaction_value,
  t.type        AS transaction_type,
  t.occurred_at AS transaction_occurred_at
FROM customers c
JOIN wallets w ON w.customer_id = c.id
LEFT JOIN transactions t ON t.wallet_id = w.id
ORDER BY t.occurred_at DESC;
ℹ
Views vs. Materialized Views: views comuns recalculam o resultado a cada consulta — refletem sempre os dados mais recentes, mas podem ser lentas sob carga alta. Materialized views armazenam o resultado em disco e precisam ser atualizadas manualmente. Para este projeto, usar views comuns mantém a implementação simples e garante que a latência de replicação seja a única fonte de atraso. O TCC pode explorar isso como variável nos testes de carga.

Filtros e ordenações

Como os dados já estão desnormalizados na view, filtros e ordenações são WHERE e ORDER BY diretos:

● Read DB — exemplo de query com filtros
-- Listagem com filtros: clientes de um gerente, saldo acima de X, sem movimentação recente
SELECT * FROM customer_view
WHERE account_manager_id = 'uuid-do-gerente'
  AND total_balance >= 500000
  AND last_transaction_at < NOW() - INTERVAL '60 days'
ORDER BY total_balance DESC
LIMIT 20 OFFSET 0;

-- Sem nenhuma lógica em código de aplicação. O banco faz todo o trabalho.

16. Critérios de Aceite

Write App

  • Invariante de horário: command RegisterTransaction fora da janela 08h–19h ou em fim de semana deve ser rejeitado com erro de domínio
  • Invariante de valor: command com value ≤ 0 deve ser rejeitado
  • Atomicidade: INSERT em transactions e UPDATE em wallets.balance ocorrem na mesma transação — nenhum dos dois persiste se o outro falhar
  • Consistência do banco write: após qualquer command aceito, o banco write reflete o novo estado corretamente (balance = soma cumulativa das transações da wallet)

Replicação

  • Subscrição ativa: após configuração, mudanças no banco write aparecem no banco read sem nenhuma intervenção manual
  • Latência mensurável: é possível medir o delta de tempo entre o commit no banco write e a disponibilidade no banco read — este é o dado central dos testes de carga do TCC
  • Sem foreign keys no read: as tabelas replicadas no banco read não têm constraints de foreign key, evitando erros de ordenação na entrega
  • Sincronização inicial: ao criar a subscrição, o banco read recebe todos os dados existentes automaticamente antes de iniciar o streaming

Read App

  • CustomerView completo: a view customer_view retorna nome, gerente, região da filial, saldo consolidado e data da última transação em uma única query
  • Múltiplas carteiras: cliente com 2 wallets tem total_balance como soma de ambos os saldos
  • Filtro por saldo: WHERE total_balance >= valor retorna apenas clientes com saldo acima do filtro
  • Filtro por última transação: WHERE last_transaction_at < data retorna apenas clientes sem movimentação desde a data
  • Perfil admin: a Read App verifica is_admin do gerente antes de permitir ListAllCustomers
  • Consistência eventual verificada: após uma transação ser confirmada no banco write, a Read App deve refletir o novo saldo em tempo mensurável — este tempo deve ser registrado durante os testes de carga

Qualidade de código (para análise SonarQube)

  • Complexidade ciclomática individual de métodos deve ser mantida baixa — a simplicidade desta arquitetura deve se refletir em handlers mais curtos que no ES
  • Cada aggregate deve ter responsabilidade única — validação de negócio separada de persistência
ℹ
Nota para o TCC: esta implementação foi desenhada para ser funcionalmente equivalente à do Event Sourcing — mesmos aggregates, mesmas invariantes, mesmo domínio — mas com código de infraestrutura significativamente menor. A diferença mensurável pelo SonarQube deve aparecer principalmente nas camadas de Command Handler (sem Event Store, sem publicação em fila) e na ausência completa da camada de Consumer e Projeções.
